# K5 — the tablet KDS

Plan of record: `docs/pos-kiosk-kds-offline-2026-08-15.md` §K5. Canon: **ECOSYSTEM §23, §22.1**.
Started 2026-08-16, immediately after K4.

## Why the lane logic came first

The stage brief's proof is *"lane logic tests ported from `KdsLanesTest`/`KdsAdvanceTest` so the two
KDS implementations cannot drift."* Two screens showing one kitchen is the risk this stage carries,
so the shared semantics land and are pinned **before** any pixel — a board built first and reconciled
later is a board that has already drifted.

## The rule the web board paid for, restated here

**A lane is a presentation choice. A transition is a state-machine fact.**

The web board draws `accepted` in the Preparing lane. A lane-keyed advance map therefore offered
every one of those cards `preparing → ready`; the state machine has no such move, so the RPC refused
it as `bad_transition` — **permanently**, because the status never changed and a refresh could not
help. The whole kitchen board was stuck (bug B1, 2026-08-06).

`KdsLane.advanceFor` is keyed on **status** for that reason, and a test walks every status × mode
pair asserting the board can never offer a move `StatusGuard` would refuse. That assertion is the
one that would have caught B1 before it reached a kitchen.

> **RESULT — K5.6 client half DONE 2026-08-16.** `packages/pos_cloud/lib/src/relay_channel.dart` +
> `test/relay_channel_test.dart`, **6 tests**, pos_cloud **44/44**, app 420/420, analyze clean.
> `RelayChannel` is the seam (same shape as `PosCloudGateway`); `CloudRelayBackendOverChannel` adapts
> it to K3c's `CloudRelayBackend`; `SupabaseRelayChannel` is the only class that touches a
> `SupabaseClient`. `pos_cloud` now depends on `pos_link`, so the transport, hub listener and route
> selector stay pure Dart and only this package knows Supabase exists.
>
> **Every test here covers something K3c's fake could not.** That fake was a two-ended pipe that
> never echoed to its sender; a Realtime branch channel is a **bus** that does both. So:
>
> - **Own-echo suppression.** A broadcast channel may deliver a message back to its sender. Nothing
>   above breaks on that today (a device's own frames fall through the type switch), but the hub
>   would add *itself* to `verifiedPeers` and — now that it publishes a board to every verified peer
>   — quietly publish boards to itself. Suppressed here so it is never discovered on a live branch.
> - **Suppression keys on the send, not on the bytes.** An identical frame from a *peer* still
>   arrives, and a *failed* publish removes its own entry — retries produce byte-identical frames, and
>   a permanent byte filter would swallow the retry it was meant to allow.
> - **Every device on the branch sees a peer frame**, which is exactly why the hub signs one board per
>   verified peer rather than broadcasting one.
> - **A channel error is forwarded** while a bad frame is not: a dead channel is route evidence, a
>   malformed frame is noise (the K3c review's DoS finding).
>
> Two things the real client forced, neither visible in the seam: `RealtimeChannel.subscribe()` is
> **not a Future** — it reports the join through a callback — and `sendBroadcastMessage` on a channel
> that has not joined is **dropped**, so the join is awaited through a `Completer`. A
> fire-and-forget subscribe would silently lose whatever the hub published in the first moments after
> a reconnect, which is precisely when there is a backlog.
>
> ## ⚠ BLOCKER FOUND — the approved posture is not directly implementable yet
>
> **Supabase Realtime authorizes a private channel from the connection's JWT. These devices have no
> Supabase session.**
>
> The whole POS cloud adapter authenticates **per RPC with a device key** — `fn_resolve_pos_device`
> hashes it and resolves the branch and role. There is no sign-in anywhere: the hub holds an anon-key
> client, and the kiosk and KDS entrypoints deliberately initialise no Supabase session at all,
> because a tablet in a public room must not carry a customer identity.
>
> That is the right design for RPCs and it is exactly wrong for Realtime. RLS on `realtime.messages`
> evaluates against the connection's role and claims; with an anon key and no session there is
> **nothing in the JWT that names a branch**, so a policy cannot tell branch 1's tablet from branch
> 2's — or from anyone else holding the publishable anon key. A private channel whose policy cannot
> distinguish subscribers is a public channel with extra steps.
>
> **No migration was written for this**, deliberately. A policy that authenticates nobody would look
> like the control the owner approved while providing none of it, and it would be discovered on a
> live branch.
>
> ### The path, for the owner to confirm
>
> **An edge function that exchanges a device key for a short-lived JWT carrying `branch_id`.** The
> device calls it with the key it already has, gets a token whose claims name its branch and role,
> and passes that to `SupabaseClient` for the Realtime connection only. The RLS policy on
> `realtime.messages` for `pos-relay:<branch>` then keys off that claim — which is the owner's
> approved posture ("authorized server-side per device key, own branch only") implemented honestly.
>
> Costs to state plainly: one edge function, a token lifetime and refresh to choose (the tablet may
> be offline for hours and must reconnect without a human), and `fn_resolve_pos_device` gaining a
> second caller. The alternative — anonymous sign-in plus a `device_sessions` table mapping
> `auth.uid()` to a branch — avoids custom JWT signing but puts a real auth user on a public tablet,
> which is the thing §23 has avoided everywhere else.
>
> Until this is decided, `SupabaseRelayChannel` is **correct client code with no server to talk to**.
> Everything above it is proven; nothing below it exists.
>
> ⚠ **The rest of the server-side half is NOT done and cannot be faked here.** `SupabaseRelayChannel` names the
> topic and asks for `private: true`; it **cannot enforce the policy**. Pointing it at an
> unauthorized topic would work perfectly while leaking every ticket on the branch. The RLS policy on
> `realtime.messages` for `pos-relay:<branch>`, keyed by the device's branch, is owed — with the
> ECOSYSTEM §23.11 append — before this ships.

## ⚠ A gap this stage found, which is not K5's to fix quietly

**`PosOrder` carries no fire time, so the `scheduled` lane can never fill.**

`pos_core` was built for the kiosk, whose take-away tickets are never scheduled — so the omission was
correct for K2. But `mergeRemoteOrder` syncs **web** orders down to this board, and a scheduled web
order arriving without its fire time lands in the *new* lane: **a cook making an 8pm order at noon**,
which is exactly what the scheduled lane exists to prevent. It also ages from `placedAtDevice`, so it
would arrive **red** — the same defect the scheduled-order pass already found and fixed on the web
board (memory `timma-scheduled-alarm-2026-08-15`), reappearing on the tablet by omission.

Closing it needs `fire_at` on `PosOrder` **and** on the store schema — a `pos_core` change with a
migration, not a UI change, which is why it is recorded rather than improvised here.
`KdsSla.agedFrom` is deliberately a one-line expression so that when the field lands, every lane,
sort and alarm inherits it at once.

**Until then the tablet board must not be pointed at a branch that takes scheduled orders.**
